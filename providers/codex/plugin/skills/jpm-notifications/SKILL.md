# JPM Payments Notifications

Guide a merchant through integrating J.P. Morgan Payments **Notifications** — real-time,
asynchronous webhook callbacks about events they subscribe to (payouts, disputes, payment
updates, refunds, and more). Authentication is assumed to be in place; this skill reuses the
`getAccessToken()` auth module produced by the `jpm-oauth` skill and never re-implements OAuth.

## Prerequisite A — Auth via `jpm-oauth`

The merchant needs a working auth module that exposes `getAccessToken()` (or its language
equivalent), produced by the `jpm-oauth` skill. Every Notifications API call uses
`Authorization: Bearer <access_token>` from that module.

- If you arrived here from `jpm-oauth`, the auth module path is already in conversation context — use it.
- If invoked standalone, ask:
  - Question: "Is JPM OAuth already wired up in this project (a working `getAccessToken()`)?"

Do **not** collect or persist credentials here. The auth module already reads them from `.env`.

## Prerequisite C — LIVE-API policy (making runtime API calls)

> This is distinct from Prerequisite B. LIVE-DOC = fetching PDP documentation pages.
> LIVE-API = calling the Notifications service API (subscriptions, notifications, etc.).

This skill does not run a server and ships no Python to execute. API calls happen in one of two
ways — pick per the merchant's intent:

- **Manual or exploratory calls**: execute [templates/notifications.http](templates/notifications.http)
   in a supported HTTP client, or issue a terminal request from
   [templates/curl-examples.md](templates/curl-examples.md).
- **Production behavior**: generate merchant-native code that calls the API using
  `getAccessToken()` — a subscription client and/or a webhook receiver. See
  [references/webhook-handler.md](references/webhook-handler.md).

**Ready-to-run requests (Bruno):** the supported subscription requests live in the
[Notifications Bruno collection](https://github.com/jpmorgan-payments/api-collections/tree/main/merchant-services/Notifications),
folder `merchant-services/Notifications/`:

- `Subscribe to a notification.bru`
- `Get all subscriptions by entity Id.bru`
- `Get a subscription by subscription Id.bru`
- `Update a specific subscription.bru`
- `Delete a specific subscription.bru`
- `Get all notification event types available.bru`
- `Get a public key by entity Id.bru`
- `Health check for the Notification Subscription service.bru`

Treat the collection as the canonical, more-frequently-updated reference for covered request bodies,
headers, and responses. Use it to learn or update the request shape, then execute the actual call
through the local HTTP or terminal templates. Configure those requests with the CAT base URL and a
token returned by the merchant's `jpm-oauth` module. Never print full tokens back to the user.
Operations not listed above are documented in [references/api-and-types.md](references/api-and-types.md).
